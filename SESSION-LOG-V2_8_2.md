# SESSION LOG v2.8.2, the watched-history rework (Claude Code, 26 July 2026)

One round, one push. Briefed as the stats-redesign session, but the audit split the brief in two: the owner's long voice note carried a second, separate body of work about the watched history, and it was bug-shaped, in the daily path and smaller than the stats redesign. The recommendation was two pushes, history first as v2.8.2 then stats as v2.9.0, so there would be two chances to catch a touch bug on the live site instead of one and a smaller thing to undo if a deploy went wrong. The owner agreed to both the split and the sequence, and confirmed the stats direction is Wrapped *language* (big numbers, bold colour, punchy headline stats), not Wrapped *format* (a swipeable one-stat-per-screen deck), which would have deleted the working drill-downs. The stats redesign is deferred to v2.9.0 in a fresh session with that direction already agreed.

## What shipped

Six behaviour changes to the watched history plus one performance fix, all in `ShowsTab.jsx`, `shared.jsx` and `styles.css`. No schema change, no new dependency, ImportWizard untouched.

**Newest at the bottom, opening at the newest end.** The history panel hangs above the page, so newest-at-bottom puts the latest episode nearest the content and makes it the first thing the pull reveals; scrolling up walks backwards in time. `history()` returns newest-first, so the display list is reversed. Opening (by pull OR by tapping the handle) scrolls to the panel's far end and leaves a 96px strip of the tab visible, which doubles as the "there is more below" cue. Implemented as a `useLayoutEffect` keyed on `histOpen` with an `openAtEnd` ref, using `behavior:'auto'` for the v2.7.7 embedded-browser reason.

**Fifteen per page, further pulls load older.** `HIST_PAGE = 15`. A second pull at the TOP of the open panel, or a "▲ Older episodes" button at the same spot, prepends the next fifteen; both pages stay mounted. "Is there more" is exact, not guessed: `history()` is asked for `pages*15 + 1` and the extra row is the end-of-list sentinel, which matters because `history()` silently drops entries whose show was removed, so a short slice does not by itself mean the end. Paging and reversal are an Episodes-view idea only; "By show" is a chronology-free aggregate and stays whole.

**Scroll-position correctness, the trap the audit led with.** Removing content above the viewport shrinks the page under the reader. The auto-condense (the owner's "when I reach the titles it packs itself away") waits until scrolling has gone idle for 140ms, then, IF the panel's bottom is above the viewport, closes it and restores the scroll position. The fix that browser verification forced: the restore target is computed BEFORE the collapse, not after. The first build subtracted the panel height from `scrollY` in the post-collapse layout effect and threw the viewport to the top of the page every time; driving it in a real 375px browser showed why, the moment the panel leaves the DOM the page gets shorter and the browser clamps `scrollY` to the new maximum immediately, so the effect was subtracting from an already-clamped value. Verified fix: a fixed probe element moved by one pixel across a condense. `overflow-anchor:none` on the panel stops the browser applying a second correction of its own; the panel uses `padding-bottom` not `margin-bottom` because `offsetHeight` excludes margin and the arithmetic depends on it.

**Tab switch already discarded the open panel** (the tab unmounts), which the owner had observed and asked to keep true. Verified live rather than "fixed"; the page count also resets to 1 on close so returning never lands on a stale 30-row scroll.

**Responsiveness, the diagnosed cause.** The pull used to `setPull` on every touchmove, re-rendering the whole tab, which re-ran `history()` (sorts the full ~10.5k-entry log), `watchNextList()` and `showProgressList()` (walk ~300 shows) roughly sixty times a second while a thumb moved, and animated the hint's `height`, reflowing every frame. Now: the three store reads are `useMemo`d on the store revision (`Store.getRev()`), so they run when the data changed and not when local UI state did; the gesture writes `transform` and `opacity` straight to the DOM (composited, no React render, no reflow); the hint is a position:absolute strip faded in by opacity rather than a growing spacer. Damping raised 0.5 → 0.75 (80px of finger earns the 60px commit, was 120px).

**The lift-and-fade, 150ms → 300ms** on the owner's request that the travel-up be more evident. The CSS `swipe-fly` duration and the JS `SWIPE_FLY_MS` delay are held to the same literal in both files with a cross-referencing comment in each, because if they drift the row snaps back to full opacity for a frame before the toggle fires. On the record: 300ms is about the ceiling before the delayed tick reads as lag, flagged to the owner as the one number to watch on his phone.

**The Episodes/By show toggle moved to the bottom of the panel.** With newest-at-bottom, the top of the panel is the oldest end, so a toggle there would sit thirty rows from where the reader is. The "▲ Older episodes" button is the accessible twin of the older-pull, on the standing rule that a gesture is never the only route in.

## Verification

Driven in a real 375×812 browser with synthetic touch events against a seeded 72-episode / 3-show history, reading the DOM back at each step: open lands with 15 rows E10→E24 top-to-bottom and the panel bottom at 716/812; a second pull adds 15 more with scroll held at 0; the auto-condense moved a fixed probe by one pixel; a tab round-trip left the panel collapsed. The residual console errors seen mid-session were stale HMR artefacts (old `?t=` build stamps from between edits); a fresh run-through captured `window.onerror` as empty and every step behaved. 119 node and 33 vitest green; `vite build` clean. Only `tests/swipe.test.jsx`'s settle wait changed (220ms → 400ms) to clear the longer fade; no product test asserted superseded behaviour, so none needed rewriting.

## Not reproducible from here

How 300ms feels under a real thumb, and whether the auto-condense fights iOS momentum scrolling. The condense is deliberately deferred until scrolling stops so it cannot fight momentum, but Safari's momentum is the one thing the desktop browser does not reproduce. Both are checklist items.
